# FastExcel benchmarks

[BenchmarkDotNet](https://benchmarkdotnet.org/) suites measuring read and write throughput and,
more importantly, **memory**. The library's stated selling points are speed and a "small memory
footprint while running", and neither had ever been measured.

```bash
# everything (slow — takes a while)
dotnet run -c Release --project FastExcel.Benchmarks -- --filter *

# one suite
dotnet run -c Release --project FastExcel.Benchmarks -- --filter *ReadBenchmarks*

# quick numbers while iterating on a fix
dotnet run -c Release --project FastExcel.Benchmarks -- --filter *ReadBenchmarks* --job Short
```

Benchmarks are **not** part of CI. They take minutes and are timing-sensitive; the CI signal for
performance comes from the allocation budgets in `FastExcel.Tests/Performance`, which are
expressed in allocated bytes and therefore hold on any machine.

Workbooks are generated by `LargeWorkbook` (shared with the test suite, so both measure exactly
the same files) and cached in the temp directory, so generation is never inside a measurement.

## Suites

| Suite | Measures |
| --- | --- |
| `ReadBenchmarks` | Reading every cell, 1k–50k rows × 10/20 columns, shared-string vs numeric payloads |
| `DefinedNameScalingBenchmarks` | How read cost scales with the number of defined names |
| `WriteBenchmarks` | Writing 1k–50k rows, numeric vs string |

## Baseline, August 2026

Recorded on the pre-fix code so the Phase 3 work has something to beat. 4-core Linux container,
.NET 8, `--job Short`.

### Reading

Roughly **1,280 bytes allocated per cell**, near-constant across workbook sizes and both payload
types — about **400× the size of the file being read**. Throughput is around **230,000
cells/sec**, and both time and memory scale linearly with cell count.

A 2.59 MB workbook (50,000 × 20) allocates **1.22 GB**. Extrapolating to the 50 MB file in #70
gives roughly 20 GB, consistent with the 12 GB reported there.

### The defined-name cliff

Same 100,000 cells, varying only how many defined names the workbook declares:

| Defined names | Mean | Allocated |
| ---: | ---: | ---: |
| 0 | 401 ms | 122.55 MB |
| 10 | 633 ms | 383.33 MB |
| 100 | 2,506 ms | 2,634.27 MB |

**100 defined names make the same read 6× slower and allocate 21× more** — 2.6 GB to read a
0.26 MB file. Cost grows linearly with the number of names, at roughly 25 MB per name per
100k cells.

The cause is in `Cell`'s constructor, which for **every cell** calls both
`DefinedNamesExtensions.FindColumnName` and `FindCellNames`. Each runs a LINQ scan over the whole
defined-name dictionary and allocates a `ToUpper()` string, a concatenated reference string and
(for `FindCellNames`) a `List<string>` — so the read is O(cells × names) instead of O(cells), and
the per-cell allocation is paid even when a workbook declares **no** defined names at all.

This matters more than it might sound: Excel creates defined names on its own for print areas and
tables, so this is an ordinary workbook, not a pathological one.

### Where the per-cell cost goes

Per cell, before any of the above: two `Regex.Replace` calls to split the reference, a retained
`XElement` (which keeps the entire parsed `XDocument` alive), a boxed value, and the two
defined-name lookups. Cheap wins in rough order of payoff:

1. Short-circuit both lookups when the defined-name dictionary is empty.
2. Index defined names by sheet/column/row instead of scanning them per cell.
3. Parse cell references by hand rather than with `Regex`.
4. Stop retaining `XElement` on every cell, or move to a streaming `XmlReader` read path.
